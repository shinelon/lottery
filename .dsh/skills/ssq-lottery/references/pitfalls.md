# 踩坑记录（改代码前先读）

这五个问题都是本次建设中真实踩到并修掉的。改 `ssq.py` 时别把它们改回去。

## 1. Python urllib 抓不到数据

**现象**：官方接口在浏览器/Code Mode 里返回 200，但 `urllib.request` 报
`HTTP Error 403`；带上 Referer 后变成 `SSL: UNEXPECTED_EOF_WHILE_READING`。

**原因**：本机网络层对 Python 的 TLS 请求做了拦截，不是目标站点的问题。

**修法**：`http_get()` 优先调用系统 `curl.exe`（`shutil.which` 定位），
失败再退回 urllib。curl 的 stderr 要截断后再抛出，否则报错信息带着整段 HTML。

```python
curl = shutil.which("curl.exe") or shutil.which("curl")
cmd = [curl, "-sS", "--max-time", str(timeout), "-A", UA, "-e", referer, url]
```

## 2. 零分布选错，把方差当优势

**现象**：蓝球 28 次命中（期望 12.5）看起来是 4.6σ，结论「显著优于随机」。

**原因**：方案每期只压 2 个蓝球（3:2 分配），单期命中数只能是 0/2/3，
方差远大于「200 注各自随机蓝球」。用后者（1σ≈3.4）当基准，
等于拿窄分布去衡量宽分布的结果，必然虚高。

**修法**：`monte_carlo()` 同时产出两个分布：
`blue_ind`（独立，1σ≈3.4）与 `blue_match`（结构一致，1σ≈5.3），
**判定只认 `blue_match`**。修完后 28 次变成第 99.7 百分位，合理多了。

## 3. 两套实现漂移，同一份数据算出 28 和 20

**现象**：为做参数敏感性另写了一个蓝球打分循环，用 min-max 归一化，
生产代码用分位归一化，同样的参数下一边 28 次、一边 20 次。

**原因**：逻辑重复实现，归一化方式不同 → 选出不同的蓝球 → 结果差 10 次命中。

**修法**：抽出唯一的 `blue_score_map(past, w, fw)`，
`build_features()` 和 `blue_sensitivity()` 都调它。
**只要出现「生产逻辑 + 验证逻辑」两份代码，就会漂移。**

## 4. 奖级概率表算错

**现象**：第一版报告写三等 1/63,261、四等 1/3,632、五等 1/184，全是错的。

**根因**：凭记忆填表，没回到组合数重算。分母是
`C(33,6) × 16 = 17,721,088`。

**正确做法**：用 `math.comb` 现算，别手写。

| 奖级 | 条件 | 概率 |
|---|---|---|
| 一等 | 6 红 + 蓝 | 1 / 17,721,088 |
| 二等 | 6 红 | 1 / 1,181,406 |
| 三等 | 5 红 + 蓝 | 1 / 109,389 |
| 四等 | 5 红 / 4 红 + 蓝 | 1 / 2,303 |
| 五等 | 4 红 / 3 红 + 蓝 | 1 / 129 |
| 六等 | 0–2 红 + 蓝 | 1 / 17 |
| 任意奖 | — | 6.71%（1/15） |

## 5. 见到 3σ 就下结论

**现象**：单次盲测蹦出 99.7 百分位，第一反应是「方法有效」。

**反证手段**（现在都固化进报告第 4 章）：

- **滚动窗口**：同一规则换 9 个窗口重跑，只有 4/9 跑赢期望；
- **参数敏感性**：20 组邻近参数，命中数 8–28，当前配置恰好是最大值；
- **独立重算**：换一种等价实现，28 掉到 20。

三者只要有一条不成立，就不能说「有优势」。三条都不成立时，
结论必须是**无预测能力**，且要写进报告，不能只放在心里。

## 附带教训

- 报告里的百分位用 `.1f`，别用 `.0f`：99.9 会被四舍五入成 100，看起来像满分。
- 控制台是 GBK，中文输出要 `PYTHONIOENCODING=utf-8`，写文件统一 `utf-8`（CSV 用 `utf-8-sig`）。
- 目标期号不能写死：按「最新期号 +1」，并按 20:00 停售时间顺延。
